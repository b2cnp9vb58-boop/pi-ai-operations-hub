# 架构说明

## 一个核心，三种权限等级

```text
网页控制台 ────────┐
Telegram 主人 ─────┼── 已认证任务接口 ── 控制核心 ── Claude 工具 Hook
微信只读入口 ──────┘                         │
                                            SQLite 审计库
```

真正决定一条消息能否变成任务的是控制核心，而不是某个聊天入口。核心会先保存任务状态再返回确认，并按通道隔离请求编号和回传结果。

### 网页与 Telegram

两者都属于控制入口。Telegram 的定位是应急兜底：即使反向代理、网站或桌面网关故障，它仍可以与核心通信。它只允许一个私聊主人完成配对。每一次高风险确认都绑定主人、任务和规范化后的具体操作；过期、修改或重复使用都会失效。

### 微信

微信被刻意设计成只读观察者。它使用独立密钥与身份绑定。核心只允许它读取属于自己的只读结果，拒绝它提交任务、查看事件、取消任务、批准操作或输入确认密码。即使 AI 提示词写错，这个服务端边界仍然存在。

### 工具边界

Claude 的每次工具调用都会先经由 Hook 送到核心。低风险诊断可以继续；未知调用、破坏性命令、凭据路径、配置修改和多工具批次默认拒绝，直到一次新的高风险确认被消费。

### 数据边界

SQLite 保存持久任务、追加式事件、配对状态和对话记录。数据库必须放在仓库外并限制文件权限；历史导出属于敏感运维数据。
